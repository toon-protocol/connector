## 1. A native daemon as a local chain

- **Packages exist.** The 4.0.2 release publishes `mina-mainnet` and `mina-devnet` debs to the
  signed `stable.apt.packages.minaprotocol.com` repository and the unsigned `packages.o1test.net`,
  for Debian 12 (bookworm) and Ubuntu 22.04/24.04 (jammy, noble). Ubuntu 20.04 and Debian 11 get
  nothing. Docker images are `minaprotocol/mina-daemon:4.0.2-84b8d96-<codename>-<network>`.
  CONFIRMED-DOCS ([4.0.2 notes](https://github.com/MinaProtocol/mina/releases/tag/4.0.2)). Stable
  debs are amd64 only. CONFIRMED-DOCS (LND `README.md`). No release tarball and no published Nix
  binary cache were found. The local-network README says to build with Nix and `dune`.
  CONFIRMED-DOCS ([MINA `scripts/mina-local-network/README.md`](https://github.com/MinaProtocol/mina/blob/4.0.3/scripts/mina-local-network/README.md)).
- **Inference:** CI (`ubuntu-latest`) can install the deb. A developer on a distribution with no
  deb, such as Arch, needs Docker or a Nix build.
- **The profile is picked at run time.** `node_config_profiled.ml` reads `MINA_PROFILE`, then
  `/etc/coda/build_config/PROFILE`, and accepts `dev`, `devnet`, `lightnet` or `mainnet`. With
  neither set, it fails. CONFIRMED-CODE ([MINA `src/lib/node_config/profiled/node_config_profiled.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/node_config/profiled/node_config_profiled.ml)).
  The stable lightnet image depends on this: it installs the devnet debs and writes `lightnet` into
  that file (LND `configuration/Dockerfile`, lines 93–96). CONFIRMED-CODE.
- **The minimum command line.** `mina-local-network.sh --demo` starts a single "amalgamation node"
  with `-block-producer-key <key file> --run-snark-worker <pk> --snark-worker-fee 0.001
--demo-mode --external-ip … --seed`, plus `--config-file`, `--proof-level`, `--client-port`,
  `--rest-port`, `--external-port`, `--metrics-port` and `--libp2p-metrics-port`, each a base port
  plus an offset. CONFIRMED-CODE ([MINA `scripts/mina-local-network/mina-local-network.sh`](https://github.com/MinaProtocol/mina/blob/4.0.3/scripts/mina-local-network/mina-local-network.sh),
  lines 298–341 and 1037–1047). The daemon image's own demo uses `--seed --demo-mode --proof-level
none --block-producer-pubkey <pk> --run-snark-worker <pk>` and a one-account ledger. CONFIRMED-CODE
  ([MINA `dockerfiles/auxiliary_entrypoints/01-run-demo.sh`](https://github.com/MinaProtocol/mina/blob/4.0.3/dockerfiles/auxiliary_entrypoints/01-run-demo.sh)).
  `--generate-genesis-proof` is "Deprecated. Passing this flag has no effect". CONFIRMED-CODE
  ([MINA `src/app/cli/src/cli_entrypoint/mina_cli_entrypoint.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/app/cli/src/cli_entrypoint/mina_cli_entrypoint.ml), line 491).
- **Demo mode** makes the daemon "assume we're \"synced\" to the network instantly". CONFIRMED-CODE
  (same file, line 226).
- **Time to SYNCED and first block.** Lightnet's documented figures are "~1-2 minutes" to start and
  sync, and a block "every ~20-40 seconds" at its default 20 s slot. CONFIRMED-DOCS (LND
  `README.md`). No native figure was found. UNCONFIRMED.
- **Slot time and k are runtime settings.** The runtime config's `genesis` takes `k`, `delta`,
  `slots_per_epoch`, `slots_per_sub_window`, `grace_period_slots` and `genesis_state_timestamp`;
  `proof` takes `level`, `block_window_duration_ms` (the slot time), `work_delay` and
  `transaction_capacity`. CONFIRMED-CODE ([MINA `src/lib/runtime_config/runtime_config.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/runtime_config/runtime_config.ml),
  lines 428–456). The local-network script writes `k: 10`, `slots_per_epoch: 48`,
  `grace_period_slots: 3`, `work_delay: 1` and `transaction_capacity: 2^2`, and its
  `--override-slot-time` sets `proof.block_window_duration_ms`. The lightnet image passes
  `SLOT_TIME` (default 20000) through that flag. CONFIRMED-CODE (`mina-local-network.sh` lines
  450–470 and 961–963; LND `scripts/spinup-testnet.sh` line 132). The profile defaults are: lightnet
  k 30, 20 s slots, proof level `none`; devnet uses mainnet's k 290, 90 s slots, proof level `full`.
  CONFIRMED-CODE ([MINA `profiled/lightnet.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/node_config/profiled/lightnet.ml),
  [`profiled/mainnet.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/node_config/profiled/mainnet.ml)).

## 2. A zkApp account in the genesis ledger

- A genesis account has `pk`, `balance`, `nonce`, `delegate`, `timing`, `token`,
  `receipt_chain_hash`, `voting_for`, `token_symbol`, **`zkapp`** and **`permissions`**.
  CONFIRMED-CODE (`runtime_config.ml`, lines 344–358).
- `zkapp` is `{ app_state, verification_key, zkapp_version, action_state, last_action_slot,
proved_state, zkapp_uri }`. `verification_key` is a Pickles side-loaded key in **base64**; field
  elements are decimal strings. Only `verification_key` has a default. CONFIRMED-CODE (lines
  268–340).
- On load, the daemon hashes the VK itself (`Verification_key_wire.digest_vk`). It pads
  `app_state` with zeros up to `Zkapp_state.max_size_int` only when asked to, and fails over that
  maximum. CONFIRMED-CODE (lines 730–770). Mesa raised the maximum from 8 to 32 fields.
  CONFIRMED-DOCS ([4.0.0 Mesa notes](https://github.com/MinaProtocol/mina/releases/tag/4.0.0-mainnet-mesa)).
- `permissions` covers every permission field, `set_verification_key` included as an
  `{auth, txn_version}` pair. CONFIRMED-CODE (lines 180–260). When missing fields are not ignored,
  a genesis account with no `permissions` fails: "no permissions set for account". CONFIRMED-CODE
  (lines 721–726). Whether the daemon's genesis path ignores missing fields was not traced.
  UNCONFIRMED.
- Lightnet's own `daemon.json` has 1007 accounts and no zkApp account. CONFIRMED-CODE (LND
  `configuration/mina-local-network/daemon.json`). No first-party tool was found that emits a
  genesis `zkapp` entry from an o1js build. UNCONFIRMED.

## 3. Full proofs

- **Proof level is chosen** from `--proof-level`, then the runtime config's `proof.level`, then the
  profile's value. A level of `full` on a profile that says `check` or `none` is fatal: "Proof level
  … is not compatible with compile-time proof level …". A lower level on a `full` profile is
  allowed. CONFIRMED-CODE ([MINA `src/lib/genesis_ledger_helper/genesis_ledger_helper.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/genesis_ledger_helper/genesis_ledger_helper.ml),
  lines 813–858).
- **Inference:** since the profile is read at run time (§1), a full-proof local chain is
  `MINA_PROFILE=devnet` plus a runtime config that shortens k and the slot time. No rebuild is
  needed.
- **The lightnet image follows the same rule.** `PROOF_LEVEL` (an env var, default `full`) must
  equal the image's `COMPILED_PROOF_LEVEL`, or the entrypoint refuses with "Use the devnet image
  for PROOF_LEVEL=full". CONFIRMED-CODE (LND `scripts/spinup-testnet.sh` lines 111–118;
  `configuration/Dockerfile` lines 18, 139–141). Tags `4.0.2-devnet` and `master-latest-devnet`
  are the "full proof generation" images, at 1.03 GB. No `4.0.3-*` tag exists. CONFIRMED-DOCS (LND
  `README.md`, Docker Hub).
- **What `none` skips.** The verifier at `Check` or `No_check` runs only `Common.check`. That
  checks signatures, the authorization kind and that each proof's VK hash equals the account's VK
  (`Unexpected_verification_key`, `Missing_verification_key`), and then returns `Assuming` for the
  proofs. Blockchain and transaction SNARKs are accepted unchecked. CONFIRMED-CODE ([MINA
  `src/lib/verifier/prod.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/verifier/prod.ml)
  lines 99–181; [`common.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/verifier/common.ml) lines 51–72).
- **Startup cost of `full`** was not found anywhere. LND says only "slower". At `full` the daemon
  also adds a genesis winner account by default (`genesis_ledger_helper.ml` lines 300–320).
  Whether a slot time that differs from the profile's forces fresh SNARK keys is UNCONFIRMED:
  `block_window_duration_ms` feeds the constraint constants (`runtime_config.ml` lines 416–446),
  but nobody has measured the effect. **Inference:** at `full`, every block needs a blockchain SNARK
  and every transaction needs snark work, so a 20 s slot may not keep up on a CI runner.

## 4. Several chains on one host

- Inside the lightnet image the ports are fixed: 3085 GraphQL, 8080 NGINX, 8181 accounts manager,
  8282 Archive-Node-API, 5432 Postgres, 3089 archive. CONFIRMED-CODE (LND
  `scripts/spinup-testnet.sh` lines 10–12 and 99–132). They are fixed only inside the container's
  own network namespace. **Inference:** `docker run -p 0:8080 -p 0:8181` per chain, then read the
  ports back with `docker port`, gives each chain its own host ports. Not tried.
- A single node runs `--seed`, with no peers and a libp2p identity of its own. Nothing ties two
  containers together. **Inference.**
- Natively, every daemon port is a flag, and `mina-local-network.sh` already runs several daemons
  on one host at base ports 3000/4000/5000/6000 with offsets. Each needs its own `--config-dir`.
  CONFIRMED-CODE (`mina-local-network.sh` lines 44–48 and 298–341).
- zkapp-cli's fixed container name and host ports (BATCH §6) are zkapp-cli's own, not the image's.

## 5. An in-process Rust ledger

- mina-rust's `crates/ledger` (package `mina-tree`) has `scan_state/transaction_logic` (zkApp
  command application) and `proofs/verification.rs`, which has `verify_zkapp`, `verify_transaction`
  and `verify_block`. Its verifier indices are devnet and mainnet JSON files. CONFIRMED-CODE (MR
  tree).
- It is **pre-Mesa**. Issues [#2196 "Mesa compatibility"](https://github.com/o1-labs/mina-rust/issues/2196)
  (2026-03-16) and [#2198 "Import Mesa circuits…"](https://github.com/o1-labs/mina-rust/issues/2198)
  are open. CONFIRMED-DOCS. The README says "Development of the Mina Rust Node is currently paused".
  The last release was v0.19.0, on 2026-01-20. CONFIRMED-DOCS. The crate is not published on
  crates.io (`mina-tree` does not exist there). CONFIRMED-CODE.
- **Inference:** a LiteSVM-like harness would mean forking `mina-tree`, porting Mesa's 32-field
  state and new circuits, and wrapping it in a ledger API that does not exist. Nothing first-party
  does that today.

## 6. First-party CI patterns

- **o1js** runs live tests against **one** lightnet per job, as a GitHub Actions `services:`
  container with `NETWORK_TYPE: single-node` and `PROOF_LEVEL: none`, mapping
  3085/5432/8080/8181/8282. It runs against `master-latest-lightnet`, `develop-latest-lightnet` and,
  for `main`, `mesa-rc2-lightnet`. CONFIRMED-CODE (O1JS `.github/workflows/checks.yml` lines
  543–630). Readiness is `o1-labs/wait-for-mina-network-action@v1` with `max-attempts: 60` and
  `polling-interval-ms: 10000`, a 10-minute ceiling. CONFIRMED-CODE (O1JS
  `.github/actions/live-tests-shared/action.yml`). The action's defaults are the same, on port 3085.
  CONFIRMED-CODE.
- **Lightnet's accounts manager** (`GET /acquire-account`, `PUT /release-account`) is built for
  "parallel automated tests execution" against one shared network. CONFIRMED-DOCS (BATCH §6).
- **Mina's own** `test_executive` (for example `zkapps.ml`, `verification_key_update.ml`) declares a
  genesis ledger and a proof config per test and runs on `integration_test_local_engine`, which
  writes docker-compose networks of several nodes plus snark workers. Its defaults are k 20 and
  120 s slots. CONFIRMED-CODE ([MINA `src/app/test_executive/zkapps.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/app/test_executive/zkapps.ml),
  [`integration_test_lib/test_config.ml`](https://github.com/MinaProtocol/mina/blob/4.0.3/src/lib/testing/integration_test_lib/test_config.ml)).
  No startup figure was found. UNCONFIRMED.

## 7. What #1554's open decisions need

The owner has settled four things: isolation plus fail-loudly in CI, so a slow chain may be shared
within one test process if each test uses fresh accounts and its own channels; no `LocalBlockchain`;
the zkApp's correctness is zk_toon's gate; VK correctness is checked on the gate with no chain.

### (a) The chain vehicle

|             | Native daemon (deb)                                                                | Lightnet image                                                            | In-process Rust ledger                  |
| ----------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | --------------------------------------- |
| Startup     | No figure. Demo mode syncs at once; the first block waits on the slot. UNCONFIRMED | "~1-2 minutes" to SYNCED. CONFIRMED-DOCS                                  | Would be milliseconds. **Inference**    |
| RAM         | No figure. Same daemon, without Postgres, archive or NGINX. **Inference**          | ~0.85–0.97 GB steady; docs say 4.5 GB to start (BATCH §6). CONFIRMED-DOCS | —                                       |
| Isolation   | Own config dir and ports per process. CONFIRMED-CODE                               | Own container; host ports remapped. **Inference**                         | Per test, trivially                     |
| Install     | amd64 deb on Debian 12 and Ubuntu 22.04/24.04 only. CONFIRMED-DOCS                 | Docker plus a ~1 GB image, amd64 for stable tags. CONFIRMED-DOCS          | Does not exist for Mesa. CONFIRMED-DOCS |
| Full proofs | `MINA_PROFILE=devnet`. CONFIRMED-CODE                                              | `*-devnet` tag. CONFIRMED-DOCS                                            | `verify_zkapp` exists, pre-Mesa         |

**Inference:** at 1–2 minutes a chain, "one chain per test process" means one per integration-test
binary: a `static` started once and shared through `OnceLock`, with a fresh account from the
accounts manager, or from a funded genesis key, for each test.

### (b) Genesis fixture or a deploy per run

- Genesis can hold the channel zkApp: VK in base64, `app_state`, `permissions`, balance, all
  required `zkapp` fields (§2). CONFIRMED-CODE. That needs a pinned, hash-checked JSON fragment,
  as `payment-channels` has. No tool emits one. UNCONFIRMED.
- A per-run deploy instead costs one transaction and one block of inclusion (20–40 s at lightnet's
  default slot), plus lightnet's 1.0 MINA account-creation fee
  (`account_creation_fee_int = "1.0"`, `profiled/lightnet.ml`). CONFIRMED-CODE. **Inference:** a
  deploy authorized by signature needs no proof, but someone must still hold the VK (a fixture) or
  compile it (11–58 s native, BATCH §6).
- **Inference:** one channel zkApp account in genesis serves only one channel. If each test needs
  its own channels, and a channel is a zkApp account, genesis would have to hold N of them, or the
  tests deploy anyway. The answer depends on the zkApp's account model (BATCH §3), which this note
  does not settle.

### (c) Proving cost per test

- A `none` chain still checks signatures, the authorization kind and the VK hash against the
  account (§3). CONFIRMED-CODE. **Inference:** the transaction logic (preconditions, permissions,
  nonces, balances, fees, the action and event limits) runs as at `full`, because only the verifier
  branches on proof level. That logic was not traced, so this is not confirmed.
- It does **not** catch an invalid proof, or a proof whose statement does not match the account
  update. **Inference:** by the owner's split, that is zk_toon's gate and the no-chain VK check, so
  the chain test does not need it.
- Whether the backend can submit a dummy proof to a `none` chain, so that no prover runs in the
  test, is UNCONFIRMED. If it cannot, each write costs a real o1js proof: 4–23 s native, 14–67 s in
  WASM (BATCH §6).

### (d) What `require_mina()` must cover

**Inference**, from the facts above. In CI it must panic, never skip, when any of these is missing:

- the vehicle, either the `mina` binary at the pinned version with `MINA_PROFILE` honoured, or a
  reachable Docker daemon with the image at a pinned **digest** (the tags float, and they were all
  rebuilt on 2026-10-14);
- the genesis fixture, with its hash checked;
- readiness: `syncStatus == SYNCED` and at least one block within a bounded wait. o1js allows 10
  minutes. A chain that never syncs is a failure, not a skip;
- the prover (Node and the o1js backend), unless (c) shows that dummy proofs are accepted.

### (e) A Mina leg in `local/`

- `local/` is one compose project (`name: connector`), one stack per machine, with chain profiles
  (`anvil`, `solana`) and a CI job capped at 30 minutes. CONFIRMED-CODE (`docker-compose.yml`;
  `.github/workflows/local-topologies.yml` line 64).
- **Inference:** a `mina` profile running the lightnet image fits that shape. It would cost a ~1 GB
  pull, 1–2 minutes to SYNCED, about 1 GB of RAM, and a healthcheck on `syncStatus`. But the
  connector image has no Mina backend to exercise, and any o1js prover would be one more container.
  Until both exist, the leg would prove nothing.

## Unconfirmed, and why

- **Native startup time and RAM.** No first-party figure exists, and none was measured.
- **Full-proof startup and block cadence.** LND says only "slower". Whether a changed slot time
  forces key generation was not traced.
- **Whether genesis loading ignores missing `permissions`.** The failure branch exists. The flag's
  value on the daemon path was not traced.
- **Tooling for a genesis `zkapp` entry.** None was found. A negative.
- **Dummy proofs on a `none` chain from Rust.** Not looked for in o1js or in `mina-tx`.
- **That transaction logic does not branch on proof level.** Inferred from the verifier code only.
- **Several lightnets per host.** Not tried, but no blocker was found in the image.
- **Startup time of `test_executive` networks.** Not documented.

## Recommendation per open decision

All **Inference**.

- **(a)** Lightnet image, one per test binary, shared through a `static`, with fresh accounts per
  test, pinned by digest. The native deb is the fallback if Docker in CI proves a problem; it is
  the same daemon with `MINA_PROFILE=lightnet`. Do not build on mina-rust.
- **(b)** Prefer a genesis fixture if the zkApp's design puts many channels in one account.
  Otherwise deploy per test from a pinned VK, which costs a block, not a compile.
- **(c)** Run proofs-off. It still catches signature, VK-hash and transaction-logic failures, and
  proof validity is already gated elsewhere. Find out first whether dummy proofs remove the prover
  from the test.
- **(d)** Cover Docker and the image digest (or the binary and version), the fixture hash, bounded
  readiness, and the prover if (c) needs it.
- **(e)** Not until the connector image has a Mina backend. Then add a `mina` compose profile with
  the same image as (a).
